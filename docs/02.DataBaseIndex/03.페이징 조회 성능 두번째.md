## 페이징 조회 성능 2편

### 게시글은 페이징의 재료는 총 2가지 이다.
1. N 번 페이지에서 M 개의 게시글 ( 해결 )
2. 게시글의 갯수

### 게시글의 갯수는 어떻게 구할까?
- 게시글의 갯수는 데이터의 유무에 따라 몇 페이지까지 활성화 할지 결정하기 위해 사용된다.
- 1200 만건을 조회 한다고 가정할때, 다음과 같다면

```sql
select count(*) from articles
```

> 1초 정도 걸린다. <br/>
> 
> 고작 1200 만건의 데이터를 조회하는데 1초가 걸린다면, 데이터가 늘어날수록 더 오랜시간이 걸리게 될것이고 정상적으로 서비스하기 어려운 상황이다.. <br/>

### client 가 알아야 할 정보
- 각 페이지 마다 게시글이 30 건식 노출된다고 가정할 경우
- 사용자가 1~10 페이지에 머물러 있을땐 301 개의 데이터만 있으면 된다. ( 30 * 10 + 1)
  - 데이터가 301 개 미만이면 다음 버튼은 비활성화
- 사용자가 11~20 페이지에 머물러 있을땐 601 개의 데이터만 있으면 된다. ( 30 * 20 + 1)
  - 데이터가 601 개 미만이면 다음 버튼은 비활성화

### 공식
- (((n – 1) / k) + 1) * m * k + 1
  - 현재 페이지(n)
    - n > 0
  - 페이지 당 게시글 개수(m)
  - 이동 가능한 페이지 개수(k)
  - ((n - 1) / k)의 나머지는 버림
- n=7, m=30, k=10
  - (((7 - 1) / 10) + 1) * 30 * 10 + 1 = 301
- n=12, m=30, k=10
  - (((12 - 1) / 10) + 1) * 30 * 10 + 1 = 601

### 해결 방법 - count Query 일부만 조회하도록 변경
- count 쿼리를 일부만 조회하도록 다시 만들어보자 !

```sql
select count(*)
from (
    select article_id
    from articles
    where board_id = {board_id} limit {limit}
     ) t;
```

> count query 에서 limit 은 동작하지 않고, 전체 개수를 반환한다. <br/>
> sub_query 에서 Covering Index 로 limit 만큼 조회하고 count 하는 방식이다. <br/>
> 
> 물론, 게시글 개수를 조회 시점에 실시간으로 쿼리할 필요는 없다 <br/>
> 
> 게시글 개수를 하나의 데이터로 미리 만들어둘 수도 있다.
> - 게시글 생성/삭제 시점마다 게시글 개수를 업데이트 하는 방식
> 
> 하지만 이를 위해, 동시 요청이 발생하는 상황에서 안전하고 정확하게 처리하기 위한 방법이 필요하다.
